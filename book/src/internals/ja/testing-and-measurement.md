# テストと計測

この章では、正しさを検証するための
テスト群（ユニットテスト、適合性テスト、クラッシュ耐性テスト、整合性検査）
と、性能値を測定・記録する方法を説明します。

## 正しさを支えるテスト群

**ユニットテストとエンドツーエンドテスト**は、対象コードと同じクレートに
置かれています。`marsdb-graph` ではストレージとグラフの不変条件を、
`marsdb-query` ではクエリの構造と処理を、`marsdb` ではシステム全体の
ワークロードを検証します。LDBC Social Network Benchmark の短い読み取り
クエリを、共通のフィクスチャと実際のパラメータ置換を使って実行するテストも
あります。単にパニックしないことではなく、結果が完全に一致することを確認
します。5 万ノードのチェーン、1 万本のエッジを持つ高次数ノードの
detach-delete、インメモリ実装と照合する 2 万回のランダム操作といった
ストレステストは、通常は `#[ignore]` とし、必要に応じて明示的に実行します。

**適合性テスト**には、`marsdb-tck` から openCypher TCK を実行します。
このハーネスは、git submodule として同梱した公式 Gherkin ファイルを解析し、
各シナリオの初期グラフを作成してクエリを実行し、TCK の値比較規則に従って
期待結果と照合します。結果は pass、wrong result、unexpected behavior、
parse-rejected、runner-unsupported の 5 種類に分類します。合格率だけでなく、
失敗の種類にも重要な意味があるためです。誤った結果は正しさの問題ですが、
未実装機能をパーサが明確に拒否するのは、対応範囲の問題です。MarsDB は現在、
3,880 件すべてのシナリオに合格しています。`CYPHER_COVERAGE.md` の対応表も、
手作業ではなく実際の実行結果から生成されます。

TCK の価値は、細かな仕様上の振る舞いを発見できる点にあります。たとえば、
`DELETE r` の後でも `type(r)` を評価できること、可変長探索の BFS をまたいで
同じエッジを再利用してはならないこと、`MERGE` で束縛済み変数のプロパティを
受け入れることは、TCK のシナリオから見つかりました。コード内のコメントには
該当シナリオも記載しています。適合性テストは機械的に検証できる仕様であり、
開発者が一から考えたテストだけでは見落としやすい境界条件も網羅します。

**クラッシュ耐性**は、専用の `marsdb-crash-harness` で検証します。ただし、
対象範囲を正確に理解する必要があります。これは「レベル 1」のクラッシュ
耐性、つまり OS とページキャッシュは残ったままプロセスだけが終了する状況を
対象とし、停電は対象外です。停電ではページキャッシュも失われるため、検証には
実際のフォールトインジェクションが必要になります。

対象範囲内では、次の方法で検証します。子プロセスが連番を記録する単一
`CREATE` トランザクションをランダムな回数だけコミットし、親プロセスが予測
できない時点で子を SIGKILL します。その後ファイルを新たに開き直し、残った
番号が必ず `{1..K}` という連続した先頭部分になっていることを確認します。
欠番があればトランザクションが一部だけ反映され、重複があればコミットが二重に
記録されたことになります。親は子のコミット状況と同期しません。どの瞬間に
停止しても同じ不変条件が成立するので、プロセス間の競合がテスト自体の不具合に
ならないよう設計されています。

**整合性チェッカー**（第 4 章）は、最終的な判定にも使います。ストレステストや
クラッシュテストの最後にテーブル間の全不変条件を検査することで、「テストが
完走した」だけでなく、「ファイル内部にも矛盾がない」ことまで確認できます。

## 計測の方針

`BENCHMARKS.md` に、このリポジトリで得られた性能値と測定条件を記録します。

- **測定した値を記載する。** 推定値と外挿値は性能表へ含めません。未測定の機能には
  性能値を記載しません。

- **すべての数値に測定条件を添える。** ハードウェア、測定日、ビルド
  プロファイル、正確な再現コマンド（Criterion を使う `cargo bench -p ...`）を
  各表とともに記録します。

- **測定範囲を併記する。** 並行読み取りの表では、2 スレッドの 1.26 倍から
  8 スレッドの 1.87 倍までは伸び、その後は頭打ちになります。表の直後には、
  上限の原因になり得る、まだ切り分けられていない 2 つの要因も記載しています。
  結論もデータが示す範囲、つまり並行実行は逐次実行より安定して速いという、
  この機能の目的に必要な範囲に限定します。別の節では、ファイル使用時に fsync
  の負荷がかかる状況や、未計測の演算子など、測っていない対象も明記します。

- **マイクロベンチマークの前後をエンドツーエンドテストで挟む。** 実データ
  （28,863 ノード、166,261 リレーションシップを通常の Cypher からロード）を
  使い、ロード、検索、更新、削除までのライフサイクル全体を継続的に測ります。
  マイクロベンチマークだけでは、複数処理の組み合わせや規模によって初めて
  現れる性能低下を見逃すことがあります。

実際のワークロードを走らせる利点は、性能値を得ることだけではありません。
ライフサイクルベンチマークから、プランナの不具合が 2 件見つかりました。
ひとつは、行の値やパラメータとの等価比較で `IndexSeek` が選ばれない問題、
もうひとつは、複数ホップのパターンで開始ノードの `WHERE` 条件が走査処理まで
伝わらない問題です。計測値が不自然だったことをきっかけに、どちらも修正
されました。予想どおりの値だけを確認するのでは、ベンチマークを十分に
活用しているとはいえません。

## 継続的インテグレーション

CI では Linux、macOS、Windows でテストスイートを実行し、フォーマットと
clippy の検査、カバレッジ収集、依存パッケージのセキュリティ監査も行います。
言語バインディング用のジョブでは Python 拡張をビルドし、ワークスペースに
対してテストします。さらに Arrow 機能を有効にした C ABI もビルドします。
これはリポジトリ外にある Go バインディングを、マージ前に保護するための
検査です。Go 側の CI はこのリポジトリの `main` から C ABI をビルドするため、
この検査がなければ互換性の破壊がマージ後まで分かりません。

最終章では、設計判断そのものを変えた計測結果を取り上げます。実装した機能を
取りやめる根拠になった結果も含まれます。
