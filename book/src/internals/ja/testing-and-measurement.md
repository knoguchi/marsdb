# テストと計測

データベースが信頼を得る道は 2 つあります: 誤った答えを出せないこと、
そして自分の数値を知っていること。この章は両方の機構を扱います —
正しさのスタック(ユニットスイート、適合性、クラッシュ安全性、
整合性)と、本書がここまで静かに引用してきた計測の規律です。

## 正しさのスタック

**ユニットとエンドツーエンドのスイート**はコードの住む場所に住んで
います: ストレージとグラフの不変条件は `marsdb-graph` のテストに、
クエリの形と機構は `marsdb-query` のものに、そして完全なワーク
ロードは `marsdb` クレートのレベルに — LDBC Social Network Benchmark
の短読クエリ群を、共有フィクスチャに対する本物のパラメータ置換で
実行し、「パニックしない」ではなく*正確な*結果を表明するスイートを
含めて。ストレステスト(5 万ノードの鎖、detach-delete つき 1 万
ファンアウトのスーパーノード、インメモリのオラクルと突き合わせる
2 万のランダム操作)は既定で `#[ignore]` され、明示的に実行します。

**適合性**は openCypher TCK で、`marsdb-tck` が走らせます: 公式の
Gherkin フィーチャファイル(git submodule としてベンダリング)を
パースし、各シナリオの初期グラフを構築し、シナリオのクエリを実行し、
TCK の値意味論で期待テーブルと比較するハーネスです。すべての
シナリオは 5 つの結果 — pass、wrong result、unexpected behavior、
parse-rejected、runner-unsupported — のどれかに落ちます。「どう
失敗したか」は合格率だけより情報量が多いからです: 誤った*結果*は
正しさのバグであり、未実装機能のきれいなパース拒否はスコープの
判断です。MarsDB は現在 3,880 シナリオ中 3,880 を通過し、カバレッジ
表(`CYPHER_COVERAGE.md`)は手で維持されるのではなく実際の実行から
生成されます。

TCK の最も深い価値は、本書に名指しされないまま繰り返し現れて
いました: エグゼキュータの最も微妙な振る舞いのいくつか —
`DELETE r` を生き延びる `type(r)`、パターンを越えて可変長ホップの
BFS にまで届くエッジ同型性、束縛済み変数のプロパティを受け入れる
`MERGE` — は*シナリオによって*発見され、コードコメントは正確な
シナリオを引用しています。適合スイートは機械検査可能な仕様であり、
そのシナリオは第一原理のテスト書きでは届かない隅に届きます。

**クラッシュ安全性**には専用ハーネス(`marsdb-crash-harness`)が
あり、その正直さはモジュールドキュメントから始まります: これは
*レベル 1* のクラッシュ安全性 — プロセスの死、OS は生存、ページ
キャッシュは無傷 — であり、明示的に電源断ではありません(電源断は
ページキャッシュも失い、テストには本物のフォールトインジェクションが
要ります)。そのスコープの中での設計は真似る価値があります: 子
プロセスが単調に番号づけられたカウンタで、ランダムな数の単一
`CREATE` トランザクションをコミットし、親が予測不能な瞬間に SIGKILL
し、ファイルをコールドに開き直し、純粋に*構造的な*不変条件を表明
します — 生き残ったカウンタ値は正確に連続する接頭辞 `{1..K}` で
なければならない。隙間なし(all-or-nothing であるべきトランザク
ションが半端に適用されていない)、重複なし(コミットが二重に記録
されていない)。親は子のコミット進行と決して同期しません。キルが
どこに着地しても不変条件は成り立つからです — 競合がテストのバグに
ならないよう設計された表明です。

**整合性チェッカー**(第 4 章)は最終のオラクルを兼ねます: ストレスと
クラッシュのテストは、テーブル横断の全不変条件の完全な論理検証で
締めくくれます。「テストが通った」を「そしてファイルは一貫している」に
変換するのです。

## 計測の規律

`BENCHMARKS.md` はリポジトリの数値台帳であり、そのルールはどんな
コードにも劣らずエンジニアリング文化の一部です:

- **実測値のみ。** 推定も外挿も「速いはず」もありません。ベンチマークの
  ない機能は性能の主張を持ちません — このファイルにプレースホルダの
  行はありません。
- **すべての数値に出所。** ハードウェア、日付、ビルドプロファイル、
  正確な再現コマンド(`cargo bench -p ...`、criterion ベース)が各表に
  付属します。
- **注意事項は述べられ、埋められない。** 並行読み取りのスケーリング表
  (2 スレッドで 1.26 倍から 8 スレッドで 1.87 倍、その後プラトー)には
  それを頭打ちにしているかもしれない 2 つの未分離要因が続き、結論は
  データが支持するものにスコープされます: 並行は逐次に確実に勝つ —
  それがこの機能の*目的*です。明示的な「これらの数値のスコープ」節が
  計測*されていない*もの — ファイルバックの fsync 圧力下のスループット、
  未ベンチマークの演算子 — を列挙し、証拠の不在を沈黙ではなく可視に
  します。
- **エンドツーエンドの検査がマイクロベンチマークを挟む。** 実データ
  セット(28,863 ノード、166,261 リレーションシップ、素の Cypher から
  ロード)がロード/クエリ/更新/削除のライフサイクルゲートで、内部が
  変わるたびに再実行されます。マイクロベンチマークだけでは、規模で
  合成されて初めて現れる退行を見逃し得ます。

実ワークロードを走らせることの利得は数値だけではありません — バグの
発見です。ライフサイクルベンチマークは 2 つのプランナ欠陥(行および
パラメータ束縛の等式で決して発火しない `IndexSeek`、複数ホップ
パターンの開始ノードの `WHERE` が絞るべきスキャンに決して届かない)を
直接暴きました。どちらも、計測値がおかしく見えたから修正されたの
です。期待を確認するだけのベンチマークスイートは使われ足りて
いません。

## 継続的インテグレーション

CI は Linux、macOS、Windows でテストスイートを走らせます。フォー
マットと clippy をゲートに、カバレッジ収集、依存関係のセキュリティ
監査、そして Python 拡張をビルドしワークスペースに対してテストを
走らせるバインディングジョブ — 加えて Arrow feature つきの C ABI
ビルド。これはリポジトリ外の Go バインディングを守るマージ前検査です
(あちらの CI はこのリポジトリの `main` から C ABI をビルドするので、
これがなければ破壊はマージ後にしか発見されません)。

最終章は、判断を*変えた*計測 — 自分の機能を殺したものを含めて — を
集めます。
