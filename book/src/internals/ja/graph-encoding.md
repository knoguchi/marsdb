# グラフのエンコーディング

前章はファイルに 13 のテーブルを置きました。この章はその中のバイト列を
開きます。素材は `marsdb-graph` にあります: 値モデル(`model.rs`)、
レコードエンコーディング(`encode.rs`)、名前のインターニング
(`labels.rs`、`props.rs`)、id 割り当て(`id.rs`)。

## 値モデル

`PropertyValue` は実行時のスカラー型であり、同時に永続化される型でも
あります — 同期を保つべき別のワイヤ表現は存在しません。variant は:
`Null`、`Bool`、`Int`(i64)、`Float`(f64)、`String`、6 つの
時制型、同種要素の `List`、そしてマップ形の*クエリパラメータ*が
システムを通過するためだけに存在する `Map` variant です — Cypher は
マップをプロパティとして保存することを禁じており、クエリ層が
ストレージに届く前に拒否します。

値は [postcard](https://docs.rs/postcard) — コンパクトな serde
フォーマット(varint 整数、フィールド名なし)— でシリアライズ
されます。この選択は、心に刻むべき一方通行の互換性ルールを伴います:
postcard は enum の判別子を*宣言順*でエンコードするので、新しい
`PropertyValue` variant は末尾に追加し、既存のものは決して並べ替えも
削除もしない — さもなくば、保存済みのすべてのプロパティが黙って
誤った variant としてデコードされます。enum の宣言順はディスク上の
ABI なのです。

時制の variant 群は、動的型付けシステムに型付き値を保存するための
設計ルールを示しています: **型はストレージ境界を生き延びねば
ならない**。日付は `Int(epoch_day)` として保存してもラウンドトリップ
自体は問題ありません — しかしそれでは、保存された整数と保存された
日付が戻り道で区別不能になります。ラウンドトリップ後も*日付として*
表示され、比較され、成分にアクセスできなければならない値に、それは
許されません。だから各時制型は第一級の variant であり、表現は
ライブラリの都合ではなく整数比較のために選ばれています:

- `Date` は Unix エポックからの日数 — 日付ライブラリの型ではなく
  `i64` です。ストレージフォーマットが依存ライブラリの内部変更で
  壊れることはあり得ず、比較は整数比較です。(`i32` でなく `i64` なのは
  Cypher の拡張年範囲 ±999,999,999 がエポック日数で ±3650 億に達する
  ため。)
- `Duration` は月・日・秒・ナノ秒の 4 成分正規形です。成分が
  *交換不能*だからです: 基準日なしには「3 か月」に固定の日数は
  存在せず、`duration({months: 1})` と `duration({days: 30})` を
  1 つの比較可能なスカラーに潰せば、どちらかを日付に足した瞬間に
  黙って間違います。
- `DateTime` は UTC 時点を保存し、ゾーンは表示のためだけに保持
  します。等価と順序は時点だけで決まるので、異なるゾーンの同一時点の
  `DateTime` 2 つは等しく比較されます — Cypher と一致 — 表示は
  異なっても。名前付きゾーンのオフセットはキャッシュ*されません*
  (同じゾーンは DST 遷移をまたいで異なるオフセットを持ちます)。
  必要になったときに再導出されます。

これらはどれも同じ規律の小さな実例です: *不変条件*(比較の意味論、
正規化、範囲)を構造的にする表現を選び、表示の問題(パース、
フォーマット、暦)はそれが属するクエリ層へ押し上げる。

## インターニング: 文字列が整数になる

ラベルとプロパティ名はインターンされます: `Person` に最初に触れた
書き込みがそれに `u32` id を割り当て、双方向の対応を記録します
(`LABEL_TO_ID`/`ID_TO_LABEL`、プロパティ名は自分の対で同様)。
以後、すべてのレコード、隣接キー、インデックスキーは id で
会話します。割り当てはノード/エッジ id と同じカウンタ機構
(`id.rs::next_id`、`META` テーブル上の read-increment-write)で
呼び出し側の書き込みトランザクションの中で起こります。つまり id
割り当ては文のクラッシュ安全性境界の内側にあります: アボートされた
文が新しくインターンしたラベルはその文とともに消え、コミット済みの
状態が未割り当ての id を参照することはあり得ません。

読み取り方向には 1 つ機微があります。インターニングテーブルはそれを
必要とする最初の書き込みが遅延作成するので、一度も書き込まれていない
データベース上の読み取りトランザクションは、テーブルを「空」では
なく*欠落*として見つけます。ルックアップ関数はその特定のエラーを
「見つからない」として扱います — 正確に等価だからです。このギャップは
推測ではなく実テスト(一度も使われていないプロパティへのインデックス
宣言)で発見されました。

## レコードエンコーディング

ノードレコードはシリアライズされたマップではありません。
**ディレクトリ**です:

```text
node:  [label_count: u8][label_id: u32 × n]
       [prop_count: u16]
       [(prop_id: u32, offset: u32) × m]     <- prop_id でソート済み
       [values: postcard エンコード、ディレクトリ順に詰める]
edge:  [label_id: u32][src: u64][dst: u64]
       [prop_count / directory / values は上と同じ]
```

オフセットは values 領域からの相対で、値 *i* の長さは
`offset[i+1] − offset[i]`(最後は末尾まで)です — だから値は
ディレクトリ順に詰められねばなりません: 長さは保存されず、含意
されるのです。

自明な代替 — 名前をキーにしたプロパティマップ全体を 1 つの postcard
ブロブとしてシリアライズする — の方が単純で、自然な最初の実装
でした。ディレクトリは読み取りパスで複雑さの元を取ります: レコード
から*1 つ*のプロパティを取り出すのは、ディレクトリ上の二分探索と
その値だけの postcard デコード 1 回です。マップは構築されず、隣の
プロパティには触れず、プロパティ名の文字列は確保されません — 名前は
レコードのどこにも現れず、呼び出し側が名前キーの完全な形を本当に
必要としたときだけ id が名前に解決されます。差はこのリポジトリで
計測されています(`marsdb-storage/examples/` 以下のエンコーディング
比較ベンチマーク): 20 個中 1 個のプロパティ読み取りで **79 倍**、
全プロパティを完全に実体化する場合でさえ **7 倍**。単一プロパティ
アクセスはエグゼキュータが絶え間なく行うことです — すべての
`WHERE n.age > 30` の評価、すべての `n.name` の射影 — つまりこれが
物を言う読み取りパスです。

エンコードとデコードは、インターニングと解決の関数をトランザクション
型ではなくクロージャとして受け取ります。同じ関数が書き込みパス
(書き込みコンテキスト経由のインターン)と読み取りパス
(読み取りスナップショット経由の解決)の両方に仕え、コーデックは
どちらの存在も知りません。計測に裏づけられた実務的な詳細を 1 つ:
解決クロージャはレコード 1 件分の解決の間テーブルハンドルを開いた
まま保持します。redb のテーブルハンドルを開くこと自体が計測された
ホットコストだったからです — 修正前のプロファイルでバルクロードの
23.67% — プロパティごとに開き直す解決器は、まさにそれを再導入して
しまいます。

## 隣接キー、ふたたび

第 2 章は `ADJ_OUT`/`ADJ_IN` の複合キーをテーブル側から説明しました。
`model.rs` がもう半分を持っています。`AdjEntry`(エッジ id、相手
端点、ラベル id)はメモリ内のトラバーサル候補です — 1 ホップに
必要なすべてが、`NODES` にも `EDGES` にも触れず隣接エントリだけから
読めます。2 つのヘルパ関数がプレフィクス境界を定義します:
`adj_node_bounds(owner)` はノードが所有する全エントリ(型なし展開)、
`adj_label_bounds(owner, label)` は 1 つのリレーションシップ型
(型付き展開)。エグゼキュータのすべてのトラバーサルは、最終的に
この境界対の間のレンジスキャンに行き着きます。

第 2 章の固定幅の警告はこちら側からも繰り返す価値があります: これらの
キーがネイティブの `(u64, u32, u64)` タプルなのは、redb が固定幅
タプルを固定スロットに保つからです。同じ情報のバイトパック
`[u8; 20]` エンコーディング — 他のバイトエンコードキーとの対称性の
点では魅力的 — は、データベースファイル総サイズ 2 倍と計測されました。

## ここに*ない*もの

削除は本物の削除です — レコード、隣接エントリ、インデックスエントリは
同じトランザクションで取り除かれ、tombstone も vacuum 機構も
ありません。MVCC の旧バージョンは redb の関心事で、その copy-on-write
B-tree が回収します。id は決して再利用されず、「ダングリング id」は
設計上の機能ではなくバグだけが作れる状態であり続けます — 整合性
チェッカーもそのように扱います。

次章は書き込み文を `GraphStore` と `WriteCtx` の中まで追いかけ、
レコード、隣接、カウンタ、そして 4 種類のインデックスエントリが
1 つのトランザクションの中でどう一貫に保たれるかを見ます。
