# グラフデータのエンコーディング

前章では、データベースファイル内の 13 個のテーブルを説明しました。この章では、
各テーブルに格納するバイト列の形式を扱います。実装は `marsdb-graph` にあり、
値のモデルは `model.rs`、レコード形式は `encode.rs`、名前のインターニングは
`labels.rs` と `props.rs`、id の割り当ては `id.rs` が担当します。

## 値のモデル

`PropertyValue` は実行時のスカラー値と保存形式の両方に使います。別の転送用
表現を用意して同期させる必要はありません。variant は `Null`、`Bool`、
`Int`（i64）、`Float`（f64）、`String`、6 種類の時間型、要素型が同じ
`List`、`Map` です。`Map` はマップ形式のクエリパラメータを受け渡すために
存在します。Cypher ではマップをプロパティとして保存できないため、クエリ層が
ストレージへ到達する前に拒否します。

値のシリアライズには [postcard](https://docs.rs/postcard) を使います。
postcard はフィールド名を格納せず、整数を varint で表すコンパクトな serde
形式です。ただし enum の判別値を宣言順で記録するため、互換性に関する制約が
あります。`PropertyValue` に variant を追加するときは必ず末尾へ追加し、既存の
variant を並べ替えたり削除したりしてはいけません。順序を変えると、保存済みの
値が別の variant としてデコードされます。enum の宣言順がディスク形式の一部に
なっています。

時間型では、値を保存して読み戻した後も元の型を区別できなければなりません。
たとえば日付を Unix epoch からの日数を表す単なる `Int` として保存すると、整数と
日付を読み戻したときに区別できません。日付として表示、比較、成分取得を行うため、
各時間型を独立した variant にしています。

- `Date` は Unix epoch からの日数を `i64` で保持します。外部の日付ライブラリの
  内部表現に依存せず、整数として比較できます。Cypher が扱う年の範囲
  ±999,999,999 は epoch から約 ±3,650 億日に達するため、`i32` では足りません。
- `Duration` は月、日、秒、ナノ秒の 4 成分を正規化して保持します。これらの成分は
  相互に置き換えられません。基準となる日付がなければ 1 か月の日数は決まらないため、
  `duration({months: 1})` と `duration({days: 30})` を同じスカラーへ変換すると、
  日付へ加算したときに誤った結果になります。
- `DateTime` は UTC 上の時刻と表示用のタイムゾーンを保持します。等価比較と順序
  比較には UTC 上の時刻だけを使うため、異なるタイムゾーンで表記されていても同じ
  時点なら等しい値です。名前付きタイムゾーンの UTC オフセットは保持しません。
  夏時間によって変化するため、必要になった時点で計算し直します。

保存形式では、比較規則、正規化、値域といった条件をデータ構造そのもので保証します。
解析、書式化、暦の処理はクエリ層で行います。

## 名前のインターニング

ラベルとプロパティ名は整数 id へ変換して保存します。たとえば `Person` が最初に
書き込まれたときに `u32` の id を割り当て、`LABEL_TO_ID` と `ID_TO_LABEL` に
双方向の対応を記録します。プロパティ名も専用の 2 テーブルで同じ処理を行います。
以後、レコード、隣接情報のキー、インデックスのキーでは文字列ではなく id を使います。

id の割り当てには、ノードやエッジと同じ `id.rs::next_id` を使います。`META`
テーブルのカウンタを読み、増加させ、書き戻す処理を、呼び出し側の書き込み
トランザクション内で行います。文が中止されれば、その文が新たに登録したラベルも
取り消されます。コミット済みの状態から、未割り当ての id が参照されることはありません。

インターニング用テーブルは、最初に必要とした書き込みによって遅延作成されます。
一度も書き込まれていないデータベースでは、読み取りトランザクションからテーブルが
空ではなく未作成として見える場合があります。検索関数は、このエラーだけを
「該当する名前がない」として扱います。未使用のプロパティにインデックスを宣言する
テストから、このケースが見つかりました。

## レコード形式

ノードのレコードは、プロパティのマップ全体をシリアライズしたものではありません。
次のディレクトリ形式を使います。

```text
node:  [label_count: u8][label_id: u32 × n]
       [prop_count: u16]
       [(prop_id: u32, offset: u32) × m]     <- prop_id 順
       [values: postcard 形式、ディレクトリ順に格納]
edge:  [label_id: u32][src: u64][dst: u64]
       [prop_count / directory / values は node と同じ]
```

各オフセットは values 領域の先頭からの相対位置です。値 *i* の長さは
`offset[i+1] − offset[i]` で求め、最後の値はレコード末尾までとします。
長さを個別に保存しないため、値はディレクトリと同じ順序で格納します。

以前は、プロパティ名をキーとするマップ全体をひとつの postcard データとして
保存していました。ディレクトリ形式では、ひとつのプロパティを読むために、
prop_id 順のディレクトリを二分探索し、該当する値だけをデコードします。マップを
構築せず、他のプロパティを読まず、プロパティ名の文字列も確保しません。名前が
必要な場合に限り id から文字列へ戻します。

`marsdb-storage/examples/` の比較では、20 個中 1 個のプロパティを読む処理が
79 倍高速になりました。全プロパティを実体化する場合も 7 倍高速でした。
`WHERE n.age > 30` や `n.name` の射影では単一プロパティの読み取りを繰り返すため、
この差がクエリ実行時間に影響します。

エンコードとデコードは、インターニングと名前解決をクロージャとして受け取ります。
特定のトランザクション型には依存しません。そのため、書き込み時は `WriteCtx` から
名前を登録し、読み取り時はスナップショットから名前を解決する同じコーデックを
使えます。

名前解決用のクロージャは、1 レコードを処理する間、テーブルハンドルを開いたままに
します。修正前のプロファイルでは、テーブルハンドルを開く処理がバルクロード時間の
23.67% を占めていました。プロパティごとに開き直すと、この費用が再び発生します。

## 隣接情報のキー

第 2 章では `ADJ_OUT` と `ADJ_IN` の複合キーをテーブル側から説明しました。
`model.rs` の `AdjEntry` は、そのエントリをメモリ内で扱う形式です。エッジ id、
反対側の端点、ラベル id を持ち、1 ホップの探索に必要な情報を `NODES` や `EDGES`
テーブルを読まずに取得できます。

範囲の境界は 2 つの関数で計算します。`adj_node_bounds(owner)` はノードが持つ
すべての隣接エントリを対象とし、リレーションシップ型を指定しない探索に使います。
`adj_label_bounds(owner, label)` はひとつの型だけを対象とします。実行エンジンの
グラフ探索は、最終的にいずれかの境界を使った範囲走査になります。

キーには redb の `(u64, u32, u64)` タプルをそのまま使います。redb は固定長の
タプルを固定サイズの領域へ格納できます。同じ情報を `[u8; 20]` にパックした実装は、
データベースファイル全体のサイズが 2 倍になりました。

## この層で扱わないもの

削除時には、レコード、隣接エントリ、インデックスエントリを同じトランザクションで
取り除きます。tombstone や vacuum は実装しません。MVCC の古いバージョンは redb
が管理し、copy-on-write B-tree の処理によって回収します。

id は再利用しません。したがって、存在しない id への参照が生じるのは実装上の
不具合がある場合だけです。整合性チェッカーは、その状態をデータ破損として報告します。

次章では、書き込み文が `GraphStore` と `WriteCtx` を通る過程を追い、レコード、
隣接情報、カウンタ、4 種類のインデックスエントリをひとつのトランザクション内で
整合させる方法を説明します。
